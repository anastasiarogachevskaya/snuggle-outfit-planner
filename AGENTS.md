- Keep the public landing page isolated to landing-specific typography tokens and composition so product screens retain their established design system.
- Localize clothing text only at UI boundaries through the shared display helper; preserve wardrobe slugs and Celsius engine inputs so saved profiles and outfit rules remain compatible.
- Administrator feedback uses a protected role table and RLS; AI analysis produces review-only proposals through a streamed server endpoint and never changes recommendation rules automatically.
- Unfinished toddler (12–35 months) support is gated by `VITE_TODDLER_ROLLOUT` via `src/lib/feature-flags.ts` ("off" default, "preview" = dev/preview server only, "public" = everyone); build-time inlining keeps SSR, hydration, server and MCP paths in agreement, and the switch only hides UI/rules, never data.
- Garment details (insulation, waterproofing, availability, sleepwear shape, foot coverage, wool-leggings use) live as optional columns on `wardrobe_items` and in `wardrobeDetails` of the versioned local profile (`upgradeGuestProfile`); "unknown" means unstated and must never be inferred from the slug. Inventory stays one row per child and slug (UNIQUE baby_id, slug), so duplicates of the same garment type can't be recorded separately; un-owning sets `owned=false` rather than deleting so IDs and details survive.
- Child preferences (clothing style, nappy use, easy toilet access) live as defaulted columns on `babies` and in `preferences` of the versioned local profile (v3, compact non-defaults); they are parent-stated only and never derived from age.
- Wardrobe setup layout (what shows first, what sits behind "View all", toddler suggestions) comes only from `src/lib/wardrobe-setup-plan.ts`, shared by phone-kept and signed-in setup; it never ticks or removes items, so owned items always stay visible and saved. Guest profiles mark the app's starter list with `wardrobeSample` so it is never mistaken for the parent's own wardrobe.
- Unit tests run with bun's runner (`bun run test`); Playwright specs live in `e2e/` and run only via `bun run test:e2e`; bunfig.toml ignores `e2e/**` so the unit run never collects them. Signed-in garment-detail writes go through `src/lib/garment-details-save.ts` so they can be tested against a mocked client.
- Every outfit-recommendation consumer (signed-in Today, phone-kept trial, outfit checker, bottoms comparison, MCP tool) builds its wardrobe through `src/lib/wardrobe-eligibility.ts`: unowned rows are never used, availability filtering follows the toddler rollout switch, and saved garment details are carried alongside (never interpreted there). Signed-in Today and Wardrobe share one cache entry, so both read with `fetchWardrobeItems` to keep the same columns. The Availability question and badges show only while availability filtering is on; hiding them never writes or resets the stored value. Outfit tips name a set-aside item as "marked outgrown/temporarily unavailable" (via `setAside` from the shared module) and keep the "No … in your wardrobe" wording for unowned items only.
- Outings are described by `src/lib/outing-context.ts`: movement, outdoor activity and ground are kept separate from transport, and every recommendation consumer (Today on phone-kept and signed-in, the MCP tool, saved records via `parseOutingContext`) goes through `normalizeOutingContext` and feeds the engine with `outingEngineFields` so `situation`/`transportMode` can't disagree. Unstated values stay omitted and are never derived from age or rainfall; seat/carrier walks without a stated movement keep their seated/carried meaning.
- Clothing needs are described by `src/lib/clothing-needs.ts`: role (thermal, everyday, insulating, outerwear, socks, footwear…) and body coverage are separate, several layers may share a body area, a multi-area garment is one entry, protection comes only from parent-stated details (else "unknown"), and transport equipment is never worn clothing. Its adapters (`clothingNeedsFromRecommendation` / `withClothingNeeds`) must round-trip any Recommendation exactly, so new clothing rules can build on the model without changing legacy outputs.
- Toddler everyday tops come only from `src/lib/recommend/everyday-tops.ts` (via `mapWardrobe`'s `tops` rules, built by `recommend()` from `childPreferences`): gated by `toddlerRulesApply` and skipped for sleep, it only reorders garments already suitable for the engine's sleeve choice by clothing style / easy toilet access, ranks complete outfits before ones with a missing bottom, makes a top always bring bottoms, and never reads nappy use. Every consumer passes the saved preferences the same way (Today on phone-kept and signed-in, MCP).
- Toddler lower-body roles (thermal underlayer, everyday bottoms, outer bottoms) come only from `src/lib/recommend/thermal-layers.ts` via `mapWardrobe` on the toddler path: a thermal slot is filled only when `LayerNeed.thermal` is set (no rule sets it yet, so owning thermals never adds them), one garment never fills two roles, and the parent's wool-leggings answer comes from `garmentDetails` (the eligible wardrobe's `details`), which every consumer passes the same way.

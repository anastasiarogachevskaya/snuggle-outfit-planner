# Two-Repo Setup: Web + iOS

Yes — this is possible. The clean way is to keep the web app in its existing Lovable-synced GitHub repo and create a second, separate iOS-only repo that pulls the web source in as a git submodule. The iOS repo owns the Capacitor wrapper, Xcode project, and App Store assets; the web repo owns the Lovable/TanStack Start app.

## Repo split

| Repo | What lives there | Source of truth |
| --- | --- | --- |
| **Web repo** (existing) | `src/`, `public/`, `package.json`, `vite.config.ts`, Supabase migrations, web app code | Lovable GitHub sync — already enabled |
| **iOS repo** (new) | `capacitor.config.ts`, `ios/` Xcode project, native plugins, GitHub Actions, README for iOS | You create it separately (GitHub, GitLab, etc.) |

## How the iOS repo gets the web app

Use a git submodule pointing to the web repo:

```
layerly-ios/
├── web/                  # git submodule → github.com/you/layerly-web (web repo)
├── capacitor.config.ts
├── ios/                  # Capacitor iOS project
├── package.json
├── .github/workflows/    # iOS build + TestFlight
└── README.md
```

### Why a submodule

- The web app is the canonical source. Lovable syncs it, you never edit web code inside the iOS repo.
- Updates flow: push web changes → Lovable syncs to web repo → in iOS repo run `git submodule update --remote web` → commit the submodule bump → iOS rebuilds.
- Xcode/Capacitor finds the built web output at a stable path (`web/dist`).

### Alternatives (pick one in the plan)

- **GitHub Actions artifact**: web repo CI builds `dist` and uploads it; iOS repo CI downloads it. No submodule, but needs a release/artifact publishing step.
- **Copy-in at build time**: iOS CI clones the web repo, builds it, then runs Capacitor sync. No submodule, but slower and more coupling.

## What goes in the iOS repo

1. **Capacitor config** (`capacitor.config.ts`)
   - `appId: online.layerly.app`
   - `appName: Layerly`
   - `webDir: 'web/dist'`
   - `bundledWebRuntime: false` (modern Capacitor)

2. **Xcode iOS project** (`ios/App/`)
   - Generated by `npx cap add ios` after the first web build.
   - Bundle ID `online.layerly.app`, app icons, splash screen.

3. **Native dependencies** (`package.json`)
   - `@capacitor/core`, `@capacitor/cli`, `@capacitor/ios`
   - `@capacitor/geolocation` (replaces browser geolocation)
   - `@capacitor/status-bar`, `@capacitor/splash-screen`
   - `@capacitor/app` (for deep-link URL handling)
   - `@capacitor-community/apple-sign-in` (App Store requirement for Apple Sign-In)

4. **CI workflow** (`.github/workflows/build-ios.yml`)
   - Check out iOS repo + submodule.
   - Install web deps in `web/`, build `web/dist`.
   - Install iOS deps, run `npx cap sync ios`.
   - Build and archive in Xcode.
   - Upload to TestFlight (requires App Store Connect API key and Apple Developer team).

5. **iOS-specific documentation**
   - How to clone with submodule: `git clone --recurse-submodules git@github.com:you/layerly-ios.git`
   - How to update web code: `git submodule update --remote web && git commit web`
   - How to open in Xcode: `npx cap open ios`

## What changes in the web repo

No code changes needed for the web app to work in a Capacitor wrapper. A few small additions are helpful:

- Add a GitHub Action (optional but recommended): build the web app on every push and upload `dist/` as an artifact. This lets the iOS repo CI download a pre-built web bundle without needing Node.js in the iOS workflow.
- Keep `.gitignore` excluding `dist/` — it should not be committed in the web repo (submodule CI will build it locally).

## Deep-linking and auth

- Apple Sign-In: use `@capacitor-community/apple-sign-in` on iOS; the web version keeps the current Apple OAuth flow for the site.
- Google Sign-In: keep the web OAuth flow inside an in-app browser (SFSafariViewController).
- Magic links / password reset: configure Supabase redirect URLs to include both:
  - Web Universal Link: `https://www.layerly.online/auth-callback`
  - iOS custom scheme: `layerly://auth-callback`
- In the iOS app, listen to `@capacitor/app` `appUrlOpen` and forward `layerly://...` URLs into the web view so the existing `auth-callback.tsx` can consume the token.

## Local development workflow

1. **Web iteration**: edit in Lovable; Lovable syncs to web repo.
2. **Update iOS submodule**: in iOS repo, `git submodule update --remote web`.
3. **Build + run**: `cd web && bun install && bun run build && cd .. && npx cap sync ios && npx cap open ios`.
4. **Native iteration**: open `ios/App.xcworkspace` in Xcode, run on a device/simulator.

## What you create outside Lovable

- The iOS repo itself (on GitHub, GitLab, etc.). Lovable can only sync one repo per project, so this is a normal second repo.
- Apple Developer account (already confirmed available).
- App Store Connect API key for CI/TestFlight upload.
- Privacy policy URL for the App Store listing.
